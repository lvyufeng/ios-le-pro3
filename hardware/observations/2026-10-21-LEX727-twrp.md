# 2026-10-21 — first hardware capture (LEX727, TWRP)

**Device:** LeEco Le Pro 3, model `LEX727`, codename `le_zl1`,
serial `33e80afe`, booted into TWRP recovery with adb allowed
(`ro.adb.secure` off in this build). Bootloader state reported as
`androidboot.verifiedbootstate=orange`, so the bootloader is **unlocked**.

Method: `adb shell` reads of `/proc`, `/sys` and the **live device tree**
under `/proc/device-tree`. No probe image was flashed or booted; everything
below is what the stock/TWRP kernel already exposes.

A probe boot is still needed for the things only a pre-boot environment can
answer (CNTFRQ at EL1 entry, whether UFS is left enabled before any kernel,
the Image header this LK accepts). Those stay `[OBS]`.

---

## Confirmed, and it changes the plan

### 1. Memory is two banks, not one

Decoded from `/proc/device-tree/memory/reg` (2 address cells, 2 size cells):

| Bank | Base | Size | End |
|---|---|---|---|
| 0 | `0x0000000080000000` | `0x0000000080000000` (2.00 GiB) | `0x0000000100000000` |
| 1 | `0x0000000100000000` | `0x000000007e550000` (1.97 GiB) | `0x000000017e550000` |

`/proc/iomem` agrees: `80000000-857fffff : System RAM` and
`91600000-17e54ffff : System RAM`, with the carve-outs in between.

**Consequence:** the XNU payload cannot be placed by splitting one bank.
`sweet`'s layout (one contiguous high bank) does not apply. The loader must
pick a bank from the FDT, and the 4 KiB page tables need at least two L3
tables if anything lands in both. The plan's "high bank only" assumption is
dead.

### 2. The splash framebuffer is where the device tree said

`/proc/device-tree/reserved-memory/`:

| Node | reg |
|---|---|
| `dfps_data_mem@83400000` | base `0x83400000`, size `0x1000` |
| `cont_splash_mem@83401000` | base `0x83401000`, size `0x023ff000` |

`0x83401000 + 1080*1920*4 = 0x83401000 + 0x7e9000 = 0x83BF A000`, inside the
region. So `ZL1_FB_PHYS 0x83401000` in `probe/zl1_hw.h` is correct.

`/sys/class/graphics/fb0/virtual_size` reports `1080,3840` (double buffer);
`bits_per_pixel` is 32. The probe draws into the first 1080x1920 frame,
which is what it already does.

### 3. UFS host address confirmed, with more registers than expected

`/proc/iomem` on the live phone:

```
00624000-006264ff : /soc/ufshc@624000
00627000-00627da7 : phy_mem
00630000-00637fff : /soc/ufsice@630000
```

`0x624000` and the PHY at `0x627000` match `zl1_hw.h`. **New:** a UFS
inline-crypto engine (`ufsice`) sits at `0x630000`. The probe must not
touch it, but the XNU UFS driver will eventually have to acknowledge it
exists so it does not fight over the same requests.

### 4. Touch: both controllers are on the bus

`/sys/bus/i2c/devices/` lists `12-0020` and `12-0038` on `i2c-12`:

- `0x20` = Synaptics DSX (the one the device tree drives)
- `0x38` = the FocalTech part the EVT board file also mentioned

`/proc/bus/input/devices` confirms the active driver is `synaptics_dsx`,
plus `gf318m` (Goodix fingerprint, not touch), `qpnp_pon` (power key) and
`gpio-keys`.

**Consequence:** the touch bring-up must probe `0x20` first and treat
`0x38` as a fallback. This is now a fact, not a guess.

### 5. Linux claims no LSE atomics

`/proc/cpuinfo` `Features:` is
`fp asimd evtstrm aes pmull sha1 sha2 crc32`, with `CPU architecture: 8` and
`CPU implementer: 0x51` (Qualcomm). No `atomics` feature is advertised, and
`CPU architecture: 8` (not 8K) is the kernel's way of saying ARMv8.0.

**Consequence:** the S8 port's LSE workaround applies. XNU must be built
without LSE, and the `libfirehose_kernel` scan is needed. This was the
single biggest unknown and it is now settled.

### 6. Hardware revision is DVT1

`android.letv.hardware_version=dvt1`. The panel in use is
`qcom,mdss_dsi_s6d6fa1_1080p_video` from `androidboot.mdp.panel`, which is
one of the several zl1 panels and the one the DVT1 board file lists first.
All of them are 1080x1920, so the framebuffer geometry holds.

## Partitions (from TWRP's `/dev/block/bootdevice/by-name/`)

Present: `aboot abootbak apdp bluetooth boot bootconfig cache cdt cmnlib
cmnlib64 cmnlib64bak cmnlibbak ddr devcfg devcfgbak devinfo dip dpo dsp
factory frp fsc fsg fsg_gap hyp hypbak kernellog keymaster keymasterbak
keystore letvconfig letveui letvreserve letvsecure mdtp misc modem modemst1
modemst1_gap modemst2 modemst2_gap msadp persist pmic pmicbak ramdump
recovery recoveryconfig reserve rootconfig rpm rpmbak sec splash ssd sti
system tz tzbak userdata vendor xbl xblbak`

- `userdata` -> `/dev/block/sda10`, logical block size **4096**,
  `start=602688`, `size=51064216` sectors, so
  **first_lba = 602688, last_lba = 51666903** (194.8 GiB). Mounted as
  `/sdcard` by TWRP, 14 GiB in use.
- The whole disk (`/dev/block/sda`) is 51,666,944 sectors = 197.1 GiB.
  The owner described the phone as 64 GB; the running hardware says
  otherwise (either a modified partition table, or a different unit was
  remembered). **Recording the measurement, not the memory.** Nothing in
  the plan depended on the capacity, and the userdata geometry above is
  what the loader needs anyway.
- Unlike a typical Qualcomm phone there is **no separate `sbl1`/`bk1`**;
  bootloader pieces are `aboot`, `xbl`, `hyp`, `tz`, `rpm`, `devcfg`,
  `keymaster`, `cmnlib*`, plus `*bak` backups.
- `persist`, `modemst1/2`, `fsg`, `fsc`, `devinfo` and `misc` are the ones
  never to touch.

The iOS root will go into `userdata` (`sda10`), which erases Android's data.
That is a later, explicit step.

## Still only answerable by booting the probe

| Question | Why the host cannot answer it |
|---|---|
| `CNTFRQ_EL0` at EL1 entry | TWRP's kernel has set it up; the bootloader handoff value is what matters |
| `HCE`/`HCS` before any kernel runs | Linux has already initialised the host by the time adb is up |
| Does this LK accept our flat Image? | only a `fastboot boot` attempt proves it |
| Does it populate `linux,initrd-start/end` for a non-Android image? | the loader depends on this |
| Real EL at entry, `VBAR` state, MMU off? | same |

## What to change in the code as a result

1. `probe/zl1_hw.h`: the RAM comment claiming a single high bank is wrong;
   replace with the two measured banks.
2. `docs/bringup-plan.md`: the loader must choose a bank from the FDT, and
   the page-table plan needs two L3 tables.
3. `NOTES.md`: record this capture.
